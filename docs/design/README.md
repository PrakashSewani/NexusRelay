# NexusRelay Low-Level Design

## Purpose

This directory translates `docs/requirements.md` into implementation-level designs. The requirements document defines what V1 must do; these documents define component responsibilities, data ownership, contracts, state transitions, transactions, cache behavior, failure handling, and verification.

If a low-level design conflicts with `docs/requirements.md`, the requirements document takes precedence until both are intentionally updated.

## Confirmed Decisions

The following decisions are approved for V1:

| Area | Decision |
| --- | --- |
| Runtime topology | Separate `gateway`, `control-plane`, and `worker` Go processes |
| Containerization | Every runtime component runs in a Docker container under Docker Compose |
| Edge routing | Configuration-driven; core local profile plus optional ingress profiles |
| Reverse proxy | Traefik in the initial Compose design |
| Public/admin URLs | Validated `PUBLIC_API_BASE_URL` and `ADMIN_BASE_URL` settings |
| Reference ingress | Optional Cloudflare Tunnel profile accepted by ADR 0001; Tailscale/CoreDNS profile proposed by ADR 0002 pending platform verification |
| TLS certificates | Configurable Traefik certificate resolver; DNS-01 is one supported profile |
| Durable database | PostgreSQL |
| Ephemeral coordination | Redis; no durable business record exists only in Redis |
| Database access | `pgx` with SQL generated by `sqlc` |
| Database migrations | Repository-owned forward SQL executed by a pinned Atlas Community CLI; committed `atlas.sum`, Atlas revision history, and PostgreSQL advisory locking per ADR 0007 |
| PostgreSQL credential boundary | V1 fixes five `LOGIN` principals (`nexusrelay_cluster_admin`, `nexusrelay_migration`, `nexusrelay_gateway`, `nexusrelay_control_plane`, `nexusrelay_worker`) and five foundational `NOLOGIN` roles (`nexusrelay_schema_owner`, `nexusrelay_security_definer_owner`, and one runtime role per service). PostgreSQL 18 membership options are explicit: migration-to-owner edges are `ADMIN FALSE, INHERIT FALSE, SET TRUE`; runtime-to-runtime-role edges are `ADMIN FALSE, INHERIT TRUE, SET FALSE`. Trusted empty-volume initialization creates this closed graph; normal migrations use it and grant object/function privileges but cannot create roles. Phase 4 bootstrap runs through the control-plane login and a narrowly scoped one-time database operation |
| Entity identifiers | Application-generated UUIDv7 |
| Tenant enforcement | Organization-scoped repositories plus PostgreSQL row-level security |
| RLS context | Transaction-local organization ID set before tenant queries |
| Pre-tenant lookup | Narrow owned `SECURITY DEFINER` functions with fixed `search_path`, bounded descriptors, and per-function `EXECUTE` grants |
| Tenant relationships | Composite organization-aware foreign keys are mandatory except documented global-table and organization-root references |
| Usage durability | Request, pre-dispatch attempt, attempt usage, finalization, and transactional outbox records in PostgreSQL |
| Configuration propagation | PostgreSQL outbox plus Redis invalidation and bounded cache TTL fallback for non-security configuration |
| Critical invalidation | Parent resource deny markers plus version counters, checked without child enumeration on every relevant authorization path |
| Distributed rate limits | Fixed UTC-minute RPM/TPM windows using versioned Redis 7 Functions, idempotent TPM reservations, and fail-closed limiter epochs per ADR 0008 |
| Cryptographic process boundary | Control plane holds provider master and API-key pepper rings for synchronous creation/rotation; gateway and worker hold only the rings required by their runtime duties |
| Provider key activation | PostgreSQL global cryptographic state fences the active provider master key ID/epoch; mounted rings declare the expected epoch and mismatched processes fail readiness and secret writes |
| Browser CSRF | HMAC-derived token over a domain-separated canonical session tuple; no per-session CSRF digest is stored |
| API-key attribution | Keys reference an owner membership; request and usage facts copy immutable owner user and membership IDs |
| Go HTTP and control-plane schema tooling | Standard `net/http` with Chi; OpenAPI 3.0.3 source contract; `oapi-codegen` strict Chi bindings and `openapi-typescript` web types per ADR 0006 |
| Organization creation | Initial bootstrap and explicit deployment-operator command only in V1; tenant roles cannot grant top-level tenant creation |
| Resource authorization scope | Separate atomic `*_own` and `*_all` permissions; default role names never determine scope |
| Deployment target | Docker Compose with separate containers for proxy, web, Go processes, migrations, PostgreSQL, and Redis |

## Design Conventions

### Identifiers and Time

- Persisted IDs are UUIDv7 unless a table is explicitly documented otherwise.
- Public APIs serialize IDs as lowercase canonical UUID strings.
- Timestamps are PostgreSQL `timestamptz`, written and returned in UTC.
- Calendar budget boundaries retain their configured IANA timezone.
- Money ledgers use integer nanos of an ISO 4217 currency unit; minor units are display/input representations only. Token prices use fixed-precision integer rates; binary floating point is prohibited.

### Tenant Scope

- Organization-owned rows include a non-null `organization_id`.
- Every organization-owned unique constraint begins with or includes `organization_id`.
- Repository methods accept organization scope explicitly.
- Tenant SQL runs inside a transaction after setting the transaction-local RLS organization context.
- Global identity lookup is restricted to authentication paths and cannot return tenant resources.
- Pre-tenant identity, session, API-key, and membership resolution uses only the approved bounded database functions; application roles have no direct unscoped table access.
- Background jobs carry organization context in their durable payload and set RLS context before processing.

### State and Deletion

- Security-sensitive records use explicit status fields instead of implicit absence.
- V1 prefers revocation, disabling, or archival over destructive deletion.
- Append-only records include requests, attempts, usage facts, outbox events, and audit events.
- Mutable resources use optimistic concurrency through a monotonically increasing `version` where concurrent administration is plausible.

### Transactions and Events

- No database transaction remains open while waiting for an upstream provider or client stream.
- A state mutation and its audit/outbox event commit in the same PostgreSQL transaction.
- Outbox consumers are at-least-once; handlers must be idempotent.
- Event payloads contain identifiers and redacted metadata, never secrets or model content.
- External side effects cannot be made atomically with PostgreSQL and therefore require idempotency, retries, and observable terminal failure.

### Caches

- PostgreSQL remains authoritative.
- Cache entries include the relevant version counter values.
- Every authority-reducing mutation, including organization suspension, establishes a synchronous fail-closed Redis deny marker before database commit; outbox processing then repairs versions and publishes durable invalidation.
- Reactivation commits authoritative active state while denial remains in place; an idempotent outbox consumer advances the version and conditionally removes only the marker matching the committed resource version.
- Gateway caches use bounded TTLs so missed invalidations self-heal.
- If cache correctness cannot be established, the gateway reloads from PostgreSQL or rejects according to the subsystem failure policy.

### Errors

- Internal errors retain operation context and causes.
- Public errors use stable machine-readable codes and sanitized messages.
- Raw upstream bodies, stack traces, credentials, authorization values, prompt content, completion content, and tool arguments are never returned or logged.

### Pagination

- Append-heavy collections use cursor pagination.
- Cursors are opaque, signed or structurally validated, and encode a stable sort tuple such as `(created_at, id)`.
- Administrative lists with bounded cardinality may use cursor pagination consistently even when offset pagination would be acceptable.

## Core End-to-End Inference Flow

1. The proxy forwards `/v1/*` to `gateway` and preserves streaming semantics.
2. The gateway generates a request ID, optionally validates a separate client correlation ID, and parses the bearer API key without logging it.
3. API key authentication resolves organization and key identity, status, restrictions, and version state.
4. The gateway validates the OpenAI-compatible request into normalized domain types.
5. The gateway creates a non-dispatching eligibility/routing plan with candidate prices and maximum chargeable attempts.
6. Rate-limit reservations and all applicable durable budget reservations are checked against that immutable plan.
7. A short PostgreSQL transaction creates the request record, routing snapshot, budget reservations, and outbox event. Authenticated policy denials create a terminal request record instead.
8. Before every provider dispatch, a short transaction durably inserts the attempt in `dispatching` state. Upstream work never begins without this marker.
9. The selected adapter performs bounded work without an open database transaction; attempt completion and any attempt-level usage are persisted after each attempt.
10. For streaming, normalized events are forwarded incrementally; provider fallback stops once response content is committed. Final usage is persisted and budgets reconciled before the terminal stream event is sent.
11. A short finalization transaction writes request totals, final request state, budget reconciliation, and outbox events.
12. The worker consumes explicit per-consumer outbox deliveries to refresh analytics, invalidations, warnings, and maintenance state.
13. A reconciliation job terminates stale `in_progress` requests and conservatively reconciles every durably started attempt and reservation.

## Open Design Items

The following remain intentionally unresolved until their dedicated design or authoritative provider research settles them:

- Provider-specific completion of the supported OpenAI field matrix beyond the V1 baseline in [13-api-compatibility-matrix.md](13-api-compatibility-matrix.md).
- Provider-specific API behavior for Xiaomi MiMo and CommandCode Provider API.
- Initial external pricing data source and automated import workflow. Manual versioned pricing administration is the V1 baseline.
- Optional unsafe Redis fail-open modes. The V1 secure default is fail closed for limited keys and critical security mutations.

Open items must not be resolved implicitly in implementation. Record consequential decisions in `docs/adr/`.
