# Workers, Health, Analytics, and Audit Design

## Scope

This design defines asynchronous worker execution, outbox processing, provider health checks and rollups, analytics aggregation, immutable audit events, request/budget reconciliation, retention, and job observability.

## Worker Runtime

The `worker` container runs a supervisor with explicitly registered job types. Each job has:

```text
name
ownership mode: partitioned | singleton
schedule or event trigger
concurrency limit
timeout
retry policy
idempotency strategy
metrics
shutdown behavior
```

No job launches unbounded goroutines. Global and per-provider concurrency limits protect PostgreSQL, Redis, and upstream services.

## Job Ownership

- Outbox work is partitioned through row leases and `FOR UPDATE SKIP LOCKED`.
- Periodic singleton schedulers use PostgreSQL advisory locks or durable lease rows.
- Scheduled work enqueues/creates concrete jobs; schedule ownership and execution ownership are separate.
- Leases include expiry and owner identity so crashed workers do not hold work permanently.
- Job side effects are idempotent because a lease can expire after a side effect but before completion is recorded.

## Outbox Processing

Topic families:

```text
configuration.*
request.started
request.finalized
attempt.completed
budget.threshold_crossed
audit.recorded
provider.tested
```

Consumers:

- Cache invalidation/version publisher.
- Analytics rollup updater.
- Budget warning materializer.
- Operational event/metric handlers.

Each event has explicit `outbox_deliveries` rows, one per required consumer. Consumers track idempotency in target tables using event ID and mark only their delivery complete. One consumer cannot make the event globally complete while another required delivery is pending.

The required delivery registry is code-defined and version-tested:

| Topic | Required consumers |
| --- | --- |
| `configuration.*` | `cache_invalidator` |
| `request.started` | `operational_metrics` |
| `request.finalized` | `request_analytics_rollup`, `operational_metrics` |
| `attempt.completed` | `passive_health`, `operational_metrics` |
| `budget.threshold_crossed` | `budget_warning`, `operational_metrics` |
| `audit.recorded` | `operational_metrics` |
| `provider.tested` | `health_summary`, `operational_metrics` |

The transaction helper derives delivery rows from this registry and rejects unknown topics. Adding/removing a required consumer is a versioned event-contract change with migration/replay implications.

## Provider Health

### Inputs

Health combines:

- Active probe observations generated by the worker.
- Passive attempt observations from real inference traffic.
- Administrative enabled/disabled status, which remains separate and authoritative.

### Health Observations

```text
provider_health_observations
  id                    uuid primary key
  organization_id       uuid not null
  provider_connection_id uuid not null
  source                text not null  -- active, passive, connection_test
  operation             text null
  success               boolean not null
  error_category        text null
  latency_ms            bigint null
  observed_at           timestamptz not null
```

Observations are short-retention facts. They never contain raw error bodies or model content.

### Health Summary

```text
provider_health_summaries
  organization_id       uuid not null
  provider_connection_id uuid primary key
  state                 text not null
  success_rate_bps      integer null
  sample_count          integer not null
  latency_p50_ms        bigint null
  latency_p95_ms        bigint null
  last_success_at       timestamptz null
  last_failure_at       timestamptz null
  last_active_check_at  timestamptz null
  window_started_at     timestamptz not null
  calculated_at         timestamptz not null
  version               bigint not null
```

Summary calculation uses versioned policy defaults. V1 starts with a five-minute fast window, thirty-minute stabilizing window, minimum 20 passive samples where available, active-probe staleness of two probe intervals, and separate entry/exit basis-point thresholds stored in typed configuration. Consecutive active failures can enter `unavailable`; recovery requires the configured consecutive successes plus exit-threshold success rate. Every summary stores the health-policy version. These defaults may be tuned only through validated configuration and contract tests.

Conceptual states:

- `unknown`: insufficient or stale observations.
- `healthy`: success rate and latency within thresholds.
- `degraded`: partial failures or elevated latency.
- `unavailable`: sustained high failure rate or consecutive active failures.

### Active Probe Scheduling

- Enabled connections receive probes with jitter.
- Degraded/unavailable connections may probe more frequently within bounds.
- Authentication/configuration failures use slower probes to avoid repeated invalid credentials.
- Probe uses model listing or metadata where possible; generation probes use minimal bounded content only if authoritative documentation requires it.
- Probe concurrency is limited per provider and globally.
- Disabled connections are not actively probed except through explicit administrator tests.

### Passive Health

Durable attempt-completion transactions emit safe passive-health outbox deliveries. Final request success is not required. Client errors, budget denials, and key rate limits do not count against provider health. Provider invalid request caused by adapter/configuration is categorized separately from availability failure.

## Analytics Aggregation

### Source of Truth

`requests`, `request_attempts`, and usage facts remain authoritative. Analytics tables are derived and rebuildable.

### Rollup Grains

V1 maintains distinct hourly projections, with optional daily rollups for long ranges:

```text
request_analytics_hourly
  organization_id
  bucket_start
  dimension_type        -- organization, user, api_key, gateway_model
  dimension_id          uuid/text not null
  request_count
  success_count
  failure_count
  input_tokens_actual
  input_tokens_estimated
  output_tokens_actual
  output_tokens_estimated
  cost_nanos_actual
  cost_nanos_estimated
  currency
  latency_sum_ms
  latency_count
  latency_histogram     -- implementation-specific bounded representation
  ttft_sum_ms
  ttft_count
  primary key (organization_id, bucket_start, dimension_type, dimension_id, currency)
```

`request.finalized` is the only incremental source for request-level projections. Idempotency uses `(request_id, projection_version, dimension_type, dimension_id)`, not outbox event ID alone.

Attempt/provider utilization is a separate projection derived from `request_attempts` and attempt usage facts during checkpointed batches or rebuilds. It records attempts, successful attempts, tokens, cost, latency, error category, and provider connection/type without incrementing request totals once per fallback provider. Error/policy-denial and budget-period projections use explicit low-cardinality categories so error trends, gateway versus provider rate limits, and budget consumption are queryable without overloading the request rollup.

### Freshness

- Outbox-driven aggregation target: under five minutes.
- Worker exposes oldest unprocessed event age.
- Dashboard returns `data_through` and `generated_at` timestamps.
- If aggregation lags, UI displays stale/partial state rather than implying real-time accuracy.

### Rebuild

A bounded rebuild command/job can recompute a time range from source facts into shadow/upserted rollups. Rebuilds are tenant/time partitioned and do not lock the inference path.

## Audit Events

```text
audit_events
  id                    uuid primary key
  organization_id       uuid null
  actor_type            text not null  -- user, system, api_key
  actor_id               uuid null
  action                text not null
  target_type           text not null
  target_id             uuid null
  request_id            text null
  correlation_id        text null
  source_ip              inet null
  outcome               text not null
  change_summary         jsonb not null
  occurred_at            timestamptz not null
```

Audit insertion is append-only and occurs in the same transaction as successful administrative mutations. Failed authentication/security events may have no organization and are written through a restricted global path.

### Change Summary

- Uses allowlisted field names and before/after values.
- Secret-bearing fields become indicators such as `credential_rotated: true`.
- API key values/hashes, passwords, cookies, authorization values, provider secret config, prompts, completions, and tool arguments are impossible in the schema builder.
- Large arbitrary request bodies are never accepted as audit metadata.

### Immutability

- Application database role has INSERT/SELECT but no UPDATE/DELETE permission on audit events.
- No control-plane mutation endpoint exists.
- Retention deletion runs under a separate maintenance role and itself produces a summarized audit/operational record outside the deleted range.
- Optional hash chaining or external archival is deferred; database privilege and append-only APIs are the V1 guarantee.

## Reconciliation Jobs

### Stale Requests

Periodically find `in_progress` requests older than operation-specific maximum deadline plus grace. For each scoped request:

- Check attempts/usage/finalization state.
- Mark `abandoned`, `failed`, or `partial` based on known commitment/outcome.
- Reconcile/release budget and TPM reservations.
- Emit finalization/analytics outbox event exactly once.

### Outbox Leases

Reset expired claims, preserve attempt count, and retry. Alert when age or attempts exceed thresholds.

### Last-Used Key Flush

Read coalesced Redis activity and update monotonic key metadata. Failure affects freshness only.

## Retention

Default policies:

- Request, attempt, usage detail: 90 days.
- Health observations: shorter configurable period, such as 14 days.
- Audit events: one year.
- Hourly/daily aggregates: configurable and may outlive details.
- Sessions: remove expired/revoked records after a security retention window.
- Processed outbox rows: retain briefly for diagnosis, then delete in batches.

Retention jobs:

- Operate in bounded batches using indexed time predicates.
- Respect foreign-key/deletion ordering.
- Avoid long transactions and table-wide locks.
- Emit rows deleted, duration, oldest remaining row, and failure metrics.
- Record a summarized audit/maintenance event.

Partitioning high-volume request tables by time may be introduced before production scale if load tests justify it. It requires an ADR and must preserve organization/time indexes and RLS.

## Worker Observability

Metrics:

```text
job_runs_total{job,outcome}
job_duration_seconds{job}
job_active{job}
job_lag_seconds{job}
outbox_oldest_age_seconds{topic}
outbox_pending{topic}
provider_health_state totals by provider_type/state
analytics_data_lag_seconds
reconciliation_total{kind,outcome}
retention_deleted_total{table}
```

Metrics avoid organization/provider-connection/request IDs as labels. Logs can include IDs because logs are designed for higher cardinality and access-controlled retention.

## Failure Handling

- One job panic is recovered at the supervised job boundary, logged safely, and does not crash unrelated workers unless state may be corrupted.
- Repeated poison outbox events enter terminal failure state and alert; they remain inspectable.
- Provider probe failures update health but never affect worker readiness globally.
- Analytics failure does not block request finalization; lag becomes visible.
- Retention failure does not trigger unsafe emergency deletion.
- Redis unavailable delays invalidation publishing and last-used flushing; durable outbox remains pending and retries.

## Verification

- Multi-worker claim, lease expiry, duplicate delivery, and graceful shutdown tests.
- Health state threshold, hysteresis, stale observation, and passive classification tests.
- Analytics duplicate-event, late event, rebuild, estimated/actual separation, and freshness tests.
- Audit database privilege and secret-redaction tests.
- Stale request/reservation reconciliation tests.
- Retention batching, cutoff boundary, and foreign-key ordering tests.
